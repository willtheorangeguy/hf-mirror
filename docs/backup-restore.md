# HF Mirror — Backup and Restore

There are three distinct artifacts: the forge's mirrored repositories, local
history snapshots made before updates, and an independent backup of the running
application's state. Keep all three according to your recovery needs.

## What to preserve

| Location | Contents |
| --- | --- |
| `data/hf-mirror.db` | Accounts, sessions, settings, source connections, repository records, jobs, and events |
| `data/.encryption_secret` | Generated credential-encryption secret used by the container |
| `data/.better_auth_secret` | Auth secret when generated by the container; an explicit secret may live only in your environment |
| `data/mirrors/` | Persistent bare Git clones and their `lfs/objects` storage |
| `data/archives/REPOSITORY_ID/` | Transfer manifests, latest metadata, and timestamped metadata snapshots |
| `data/repo-backups/` | History safety bundles and JSON sidecars |
| Deployment files and secret storage | Image version, Compose overrides, environment, explicit secrets, and CA settings |
| Gitea/Forgejo data | Destination repositories, large files, issues, and forge configuration |

The data directory normally follows the SQLite file's parent directory.
`MIRROR_CLONE_DIR` and a custom `backupDirectory` can move parts elsewhere.
Back up every actual persistent path and the forge using its own procedures.

A Git bundle contains Git objects and refs, not the underlying LFS payloads.
Safety bundle sidecars explicitly say LFS objects are retained in the persistent
mirror clone. Keeping only bundles cannot restore historical model weights.

## Take a consistent application backup

For a simple Linux Compose installation, stop writes before copying the entire
directory, including hidden files. Choose an unused backup filename:

```sh
docker compose stop hf-mirror
tar -czf hf-mirror-data-backup.tar.gz data
docker compose start hf-mirror
```

Add your Compose override flags if used. Copy this archive off the host and
store the environment and explicit secrets securely. If you use a live SQLite
backup method instead, also coordinate clone, archive, and secret copies;
copying only an open `.db` file may omit committed WAL data. A stopped full
directory copy includes any SQLite sidecar files too.

## Restore an application instance

1. Stop the target instance. Preserve its current data separately before replacing it.
2. Restore the saved data directory and all custom storage paths. Restore the exact
   secrets and configuration associated with the backup.
3. Make files writable by container UID/GID 1001. Use the matching image version
   first; do not combine an older binary with an already-upgraded schema blindly.
4. Start the service and inspect migrations, credential decryption, health, and login.
5. Run destination reconciliation in preview mode, inspect differences, then sync
   a small repository before resuming scheduled work.

Reconciliation reports missing or moved managed destinations and untracked mirrors
with valid HF Mirror provenance. It can adopt, relocate, or reset selected records
when explicitly applied. It does not make missing file content reappear. If the
database is missing, restoring it is preferable to reconstructing records from
the forge.

## History protection strategies

Set `giteaConfig.backupStrategy` in Configuration:

| Strategy | Before an update of an existing destination |
| --- | --- |
| `disabled` | Skip the history protection snapshot |
| `always` | Make a safety snapshot on each run |
| `on-force-push` | Snapshot when a branch update is non-fast-forward, a ref disappears, or a tag/PR ref changes |
| `block-on-force-push` | Pause destructive changes as `pending-approval` until approved |

The default is `on-force-push`, with up to five snapshots and a 30-day age limit
per source identity. Retention runs when creating a new snapshot and keeps the
newest one. A zero age limit disables age expiration. By default, a failed
snapshot blocks the update. An empty destination needs no prior-history snapshot.

Before creating a snapshot with LFS enabled, the engine fetches destination large
files for its old revisions into the clone. It creates a hashed-name `.bundle`
and a `.bundle.json` sidecar identifying the source and previous refs.

## Inspect a safety bundle

Work on a copy of a backup and inspect the JSON sidecar first:

```sh
git bundle list-heads /backups/REPOSITORY-TIMESTAMP.bundle
git clone --bare /backups/REPOSITORY-TIMESTAMP.bundle recovered.git
git -C recovered.git show-ref
```

The bundle may contain fetched safety refs as well as source refs. Use the
sidecar's exact `refs` mapping to identify the destination history you intended
to recover. Verify the required LFS objects from the corresponding persistent
clone and test recovery in an isolated repository. There is no one-click
historical restore action. A later ordinary sync will again match the source,
so pause automation until you decide which history to preserve.

## Metadata archives and completeness

`transfer.json` records source identity, backed-up refs, large-file inventory,
and whether large files were included. Metadata writes include `latest.json`
and timestamped `metadata-*.json` files. The authenticated archive download
combines the latest metadata and transfer manifest into JSON; it is not a full
repository export.

Metadata snapshots accumulate independently of safety-bundle retention. Budget
storage and set your own archive-retention policy outside active writes. A
`mirrored` or `synced` status confirms the selected options; check that large
files were not excluded and that selected metadata finished. Destination LFS
verification checks advertised object availability and size, while local files
are checked by SHA-256. Test a real restore periodically.
